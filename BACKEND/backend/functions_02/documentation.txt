Backend Functions – API Reference
This document covers all database functions in the groups schema that implement a full ROSCA (Rotating Association) engine. The system supports group creation, rotation planning, contribution scheduling, partial payments, penalty management, automatic disbursement, and fallback to manual approval.

Core Setup & Planning
1.	create_plan
Purpose – Internal helper; creates a generic plan entry in groups.plans for any plan type (rotation, savings, loan). Usually called by other functions.
Signature
groups.create_plan(p_group_id UUID, p_plan_type_name TEXT, p_plan_name TEXT, p_plan_description TEXT DEFAULT NULL) RETURNS UUID
Parameters
•	p_group_id – ID of the group.
•	p_plan_type_name – 'rotation', 'savings', or 'loan'.
•	p_plan_name – Display name.
•	p_plan_description – Optional description.
Returns – The newly created plan_id (UUID).
Example
sql
SELECT groups.create_plan('group-uuid', 'rotation', 'Weekly ROSCA', 'Test plan');

2.	create_rotation_plan
Purpose – Creates a new rotation plan (ROSCA) inside a group. Links to a groups.plans record and stores penalty rules. The creator must be an admin of the group.
Signature
groups.create_rotation_plan(p_group_id UUID, p_created_by UUID, p_rotation_name TEXT DEFAULT 'Group Rotation', p_rotation_description TEXT DEFAULT NULL, p_start_date TIMESTAMPTZ DEFAULT now() + interval '1 day', p_penalty_type TEXT DEFAULT 'fixed', p_penalty_value NUMERIC DEFAULT 0, p_penalty_grace_days NUMERIC DEFAULT 0, p_amount_distributable NUMERIC DEFAULT 0, p_disbursement_type groups.disbursement_type DEFAULT 'auto', p_low_funds_options groups.low_funds_options DEFAULT 'approval') RETURNS JSONB
Parameters
•	p_group_id – Group UUID.
•	p_created_by – groups.group_members.id of the admin.
•	p_rotation_name, p_rotation_description – Name/description.
•	p_start_date – First contribution due date.
•	p_penalty_type – 'fixed' or 'percentage'.
•	p_penalty_value – Fixed amount or percentage (1 100).
•	p_penalty_grace_days – Days after due date before penalty applies.
•	p_amount_distributable – Total pot per cycle (optional).
•	p_disbursement_type – 'auto' (automatic when cycle complete) or 'approval' (manual).
•	p_low_funds_options – Strategy when funds insufficient (not heavily used yet).
Returns – JSON: { "rotation_plan_id": "...", "plan_id": "...", "code": "...", "status": "created" }
Example
sql
SELECT groups.create_rotation_plan(
    p_group_id := '827ab1fc-7d8c-4598-957e-80b6cffaf595',
    p_created_by := 'ef2260b2-0727-42d8-b8aa-1cae032ddafe',
    p_rotation_name := 'Weekly ROSCA',
    p_penalty_type := 'fixed',
    p_penalty_value := 100,
    p_penalty_grace_days := 2
);

3.	update_rotation_plan
Purpose – Updates rotation plan details (name, dates, penalty, etc.). Allowed only before the plan is locked (no schedules generated). Admin only.
Signature
groups.update_rotation_plan(p_plan_id UUID, p_editor_id UUID, p_rotation_name TEXT DEFAULT NULL, p_rotation_description TEXT DEFAULT NULL, p_start_date TIMESTAMPTZ DEFAULT NULL, p_penalty_type TEXT DEFAULT NULL, p_penalty_value NUMERIC DEFAULT NULL, p_penalty_grace_days NUMERIC DEFAULT NULL, p_amount_distributable NUMERIC DEFAULT NULL, p_disbursement_type groups.disbursement_type DEFAULT NULL, p_low_funds_options groups.low_funds_options DEFAULT NULL) RETURNS JSONB
Returns – { "status": "updated", "plan_id": "...", "message": "..." }
Example
sql
SELECT groups.update_rotation_plan(p_plan_id := 'plan-id', p_editor_id := 'admin-id', p_rotation_name := 'New Name');

4.	delete_rotation_plan
Purpose – Soft deletes a rotation plan (rotation_status = 'deleted'). Admin only.
Signature
groups.delete_rotation_plan(p_plan_id UUID, p_editor_id UUID) RETURNS JSONB
Returns – { "status": "deleted", "plan_id": "..." }

5.	get_group_rotations
Purpose – Lists all active rotation plans for a group. Returns penalty details and member count.
Signature
groups.get_group_rotations(p_group_id UUID) RETURNS TABLE (plan_id UUID, rotation_name TEXT, start_date TIMESTAMPTZ, status TEXT, penalty_type TEXT, penalty_value NUMERIC, penalty_grace_days NUMERIC, member_count BIGINT)
Example
sql
SELECT * FROM groups.get_group_rotations('group-uuid');

6.	get_rotation_members
Purpose – Lists active members in a rotation plan with their payout order and status.
Signature

groups.get_rotation_members(p_rotation_plan_id UUID) RETURNS TABLE (rotation_member_id UUID, group_member_id UUID, member_name TEXT, amount_receivable NUMERIC, status TEXT, payout_order INTEGER)

Rotation Members

7.	add_member_to_rotation
Purpose – Adds an active group member to a rotation plan (before lock). If the member already exists but was soft deleted, it reactivates them.
Signature
groups.add_member_to_rotation(p_rotation_plan_id UUID, p_group_member_id UUID, p_amount_receivable NUMERIC DEFAULT 0) RETURNS JSONB
Returns – { "status": "added" | "already_exists" | "reactivated", ... }
Example
sql
SELECT groups.add_member_to_rotation('plan-id', 'group-member-id');

8.	remove_rotation_member
Purpose – Soft deletes a member from a rotation plan (sets rotation_member_status = 'deleted'). Admin only, before lock.
Signature
groups.remove_rotation_member(p_rotation_plan_member_id UUID, p_editor_id UUID) RETURNS JSONB
Returns – { "status": "removed", "rotation_plan_member_id": "...", "rotation_member_status": "deleted" }

9.	update_rotation_payout_order
Purpose – Sets or updates the payout order (ROSCA sequence) for a rotation member. Admin only, before lock. Ensures orders are unique and positive.
Signature
groups.update_rotation_payout_order(p_rotation_plan_member_id UUID, p_new_payout_order INTEGER, p_editor_id UUID) RETURNS JSONB
Returns – { "status": "updated", "rotation_plan_member_id": "...", "payout_order": ... }

10.	assign_payout_order (trigger)
Purpose – Automatically assigns the next available payout order when a member is added (if none provided). Triggered before insert on rotation_plan_members.
Trigger – trg_assign_payout_order on groups.rotation_plan_members.

Contribution Schedules

11.	generate_rotation_schedules
Purpose – Creates the full contribution schedule for a rotation plan: one member_schedule_settings and one rotation_collection_schedule entry per member per cycle. After generation, the plan is locked (no further changes). Must be called before the start date.
Signature
groups.generate_rotation_schedules(p_rotation_plan_id UUID, p_contribution_amount NUMERIC, p_interval_days INTEGER) RETURNS JSONB
Returns – { "status": "schedules_generated_and_locked", "total_entries": ..., "number_of_cycles": ..., "first_due_date": "...", ... }
Example
sql
SELECT groups.generate_rotation_schedules('plan-id', 1000, 7);

12.	record_contribution
Purpose – Records a payment for a specific collection schedule. Handles partial payments, overpayments (carried to next cycle of the same member), and triggers the evaluation of cycle completion via the cron function.
Signature
groups.record_contribution(p_schedule_id UUID, p_amount NUMERIC) RETURNS JSONB
Returns – { "status": "recorded", "schedule_id": "...", "amount_applied": ..., "overpayment_carried": ..., "new_schedule_status": "partial"|"completed", "transaction_id": ... }
Example
sql
SELECT groups.record_contribution('schedule-id', 600);

Disbursement (Payout)

13.	record_disbursement
Purpose – Records a disbursement (payout) to a rotation member. Enforces ROSCA rules: only the member with payout_order = current_cycle can receive, and the pot must equal the sum of all members’ contributions for that cycle. Called automatically by the evaluation cron or manually by an admin.
Signature
groups.record_disbursement(p_rotation_plan_member_id UUID, p_amount NUMERIC, p_transaction_id UUID) RETURNS JSONB
Returns – { "disbursement_id": "...", "code": "...", "status": "disbursed", "cycle": ..., "amount": ... }

14.	evaluate_cycle_and_disburse (cron function)
Purpose – The single source of truth for cycle advancement. Runs periodically (e.g., hourly). For each locked rotation plan:
•	If the current cycle’s due date has passed and all members have completed payments, automatically disburses the full pot.
•	If the due date has passed but the total collected is less than expected, switches disbursement_type to 'approval' (manual intervention).
•	If all members have completed early (before due date), it will disburse immediately (on the next cron run).
Signature
groups.evaluate_cycle_and_disburse() RETURNS JSONB
Returns – { "processed": [ { "plan_id": "...", "action": "...", ... } ] }
Cron setup (hourly):
sql
SELECT cron.schedule('evaluate-cycle-disbursement', '0 * * * *', 'SELECT groups.evaluate_cycle_and_disburse();');

15.	get_upcoming_payouts
Purpose – Lists rotation members who have not yet received their payout (status 'pending'), ordered by expected payout cycle.
Signature
groups.get_upcoming_payouts(p_rotation_plan_id UUID) RETURNS TABLE (rotation_member_id UUID, member_name TEXT, amount_receivable NUMERIC, status TEXT, expected_payout_cycle INTEGER)

Penalties

16.	calculate_penalty
Purpose – Returns the penalty amount for a given member schedule, based on the rotation plan’s penalty_type and penalty_value.
Signature
groups.calculate_penalty(p_rotation_plan_id UUID, p_member_schedule_settings_id UUID) RETURNS NUMERIC

17.	record_penalty
Purpose – Creates a pending penalty record for a collection schedule. Usually called by apply_overdue_penalties.
Signature
groups.record_penalty(p_collection_schedule_id UUID, p_amount NUMERIC, p_transaction_id UUID) RETURNS JSONB
Returns – { "penalty_id": "...", "code": "...", "status": "recorded", "amount": ... }

18.	waive_penalty
Purpose – Allows an admin to waive a pending penalty (sets penalty_status = 'waived').
Signature
groups.waive_penalty(p_penalty_id UUID, p_admin_group_member_id UUID) RETURNS JSONB
Returns – { "status": "waived", "penalty_id": "..." }

19.	update_rotation_penalty
Purpose – Changes penalty rules (type/value/grace days) of an unlocked rotation plan. Admin only.
Signature
groups.update_rotation_penalty(p_plan_id UUID, p_admin_group_member_id UUID, p_penalty_type TEXT, p_penalty_value NUMERIC, p_penalty_grace_days NUMERIC DEFAULT NULL) RETURNS JSONB

20.	apply_overdue_penalties
Purpose – Cron function that finds 'due' schedules past their grace period and automatically applies penalties (calls record_penalty). Run daily.
Signature
groups.apply_overdue_penalties() RETURNS JSONB
Returns – { "penalties_applied": N }
Cron setup (daily at 1 AM):
sql
SELECT cron.schedule('apply-overdue-penalties', '0 1 * * *', 'SELECT groups.apply_overdue_penalties();');

Cron Jobs & Automation
Job Name	Schedule	Function	Purpose
apply-overdue-penalties	daily at 1 AM	groups.apply_overdue_penalties()	Applies penalties to overdue schedules.
evaluate-cycle-disbursement	hourly	groups.evaluate_cycle_and_disburse()	Checks cycle due dates; disburses full pot or switches to approval on partial pot.
Note: To enable cron, you must install the pg_cron extension and grant necessary permissions. In Supabase, this can be enabled in the Dashboard.

Supporting Functions (not directly exposed as API)
•	assign_payout_order (trigger) – Auto assigns payout order on member insertion.
•	create_plan – Helper to insert a generic plan.
•	update_updated_at_column – Generic trigger to maintain updated_at timestamps.

Error Handling & Validation
•	All functions raise descriptive EXCEPTION messages on validation failures (invalid roles, missing data, locked plans, capacity exceeded, etc.).
•	JSONB returns always include a status field indicating success or a specific state (e.g., 'already_exists').
•	Soft deletions are used wherever possible to preserve audit trails (deleted_at, rotation_member_status = 'deleted', rotation_status = 'deleted').

Usage Flow (Typical ROSCA)
1.	Create group (groups.create_group) – already implemented separately.
2.	Create rotation plan (create_rotation_plan) – admin sets penalty and disbursement type.
3.	Add members (add_member_to_rotation) – payout orders are auto assigned or later updated.
4.	Generate schedules (generate_rotation_schedules) – plan becomes locked.
5.	Members pay via record_contribution (partial, full, overpay).
6.	Cron jobs:
o	apply_overdue_penalties – adds penalties for late payments.
o	evaluate_cycle_and_disburse – after due date, either auto disburses (if pot full) or switches to approval mode (if pot incomplete).
7.	Admin can manually disburse using record_disbursement if plan is in approval mode.

Version & Maintenance
•	All functions are in the groups schema.
•	Search path is set explicitly to groups, public.
•	Idempotent (can be re run with CREATE OR REPLACE).
•	Proper use of FOR UPDATE locking where needed.
Plan Types (System Admin Only)
Plan types define the kind of financial product a group can run (e.g., rotation, savings, loan). They are managed by system administrators and cannot be changed by group admins.
21.	create_plan_type
Purpose – Adds a new plan type to the groups.plan_types table. Only a system administrator can execute this function.
Signature
groups.create_plan_type(p_type_name TEXT, p_type_description TEXT DEFAULT NULL, p_created_by UUID) RETURNS JSONB
Parameters
•	p_type_name – Unique identifier (e.g., 'investment').
•	p_type_description – Human readable description.
•	p_created_by – public.administrators.id of the system admin.
Returns – { "status": "created", "type_name": "...", "type_description": "..." }
Example
sql
SELECT groups.create_plan_type('investment', 'Group investment club', 'sys-admin-uuid');
Default plan types (seeded once)
sql
INSERT INTO groups.plan_types (type_name, type_description) VALUES
    ('rotation', 'Rotating Savings and Credit Association (ROSCA)'),
    ('savings', 'Group savings account'),
    ('loan', 'Group loan product')
ON CONFLICT (type_name) DO NOTHING;

 Distinction between create_plan_type and create_plan
•	create_plan_type → adds a new category of plan (e.g., 'investment'). Called rarely, by system admins.
•	create_plan → creates a concrete instance of a plan for a specific group (e.g., a rotation plan named “Weekly ROSCA”). Called by group admins when they start a new rotation.
